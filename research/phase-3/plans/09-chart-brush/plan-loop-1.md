## 2. bklit behavior inventory (file:line cited)

### 2.1 `ChartBrush` (`repos/bklit-ui/packages/ui/src/charts/chart-brush.tsx`, 344 lines)

- Thin wrapper around `@visx/brush`'s `Brush` component (`chart-brush.tsx:3,47-48` — `import { Brush } from "@visx/brush"`). This is the single largest fidelity risk: bklit's actual drag/resize/move gesture math, handle hit-testing, and window-vs-local pointer-event handling live **inside the visx library**, not in bklit's own code — there is no bklit-owned gesture implementation to literally port. TanStack has no equivalent and the migrated port must reimplement the gesture from scratch (confirmed by the task brief and by this inventory: no drag-math file exists to read).

- `brush-${innerWidth}-${innerHeight}` React `key` on the visx `<BrushComponent>` (`:238`) — **remounts the entire brush gesture on any resize**, resetting drag state; intentional per bklit (avoids stale internal visx geometry after a container resize).

### 2.3 `ChartBrushLayout` (`chart-brush-layout.tsx`, 123 lines) — the state owner

- Props (`:22-38`): `data` (full dataset), `xDataKey` (default `"date"`), `xExtentMax?: Date`, `enabled: boolean`, `height: number` (fixed strip height), `fitMainContent?`, `className?`, `children: (layout) => ReactNode` (main chart render-prop), `brushStrip?: (layout) => ReactNode` (mini-chart render-prop, only rendered when `enabled`, `:116-120`).

### 2.5 `xExtentMax` / brush-track horizon vs. initiative-7 `mergeProjectionXDomainMax` — two SEPARATE mechanisms, do not conflate

- `resolveBrushTrackXExtent(data, xAccessor, xExtentMax)` (`filter-data-by-x-domain.ts:46-59`): returns `[dataMin, xExtentMax]` if `xExtentMax` is later than the data's own max, else just the plain data extent. This ONLY affects the **brush strip's own full track range** (via `ChartBrushLayout`'s `fullExtent`, §2.3) — it lets the mini-chart's brushable track extend past the last real data point (e.g. to cover a projection horizon) so the user can drag a selection window that includes projected future dates.
- Initiative 7's `mergeProjectionXDomainMax` (migrated `internal/projection-utils.ts` / bklit's own equivalent in `projection-config.ts`, not read this session) extends the **main chart's own xScale** past the last data point when `ProjectionLine` children are present — but per §2.4, this merge is explicitly bypassed on the main chart whenever `xDomain` (brush) is active. **The two mechanisms are mutually exclusive on the main chart and additive only via the brush track**: with brush enabled, the main chart's horizon comes ENTIRELY from whatever `xDomain` the brush handles currently express (which can reach out to `xExtentMax` if the user drags that far), never from the projection-merge path directly.
- Migrated side: `internal/x-axis-overlay.tsx:7-11` already documents this gap explicitly ("Brush tail variant `appendProjectionTailTicks` intentionally not implemented (deferred to the brush initiative)") — confirming this file is the intended landing spot for §2.6 below, not a new file.

### 2.6 X-axis tail-tick behavior during brush (`x-axis.tsx:494-557`, `:596-624`)

- `appendProjectionTailTicks(ticks, data, xAccessor, xScale, marginLeft, maxExtraTicks)`: when the domain extends past the last real data point AND a brush `xDomain` is active (`:614-624`, `projectionExtendsScale && xDomain != null`), bklit KEEPS the existing data-aligned ticks (real row positions) and appends up to `min(maxExtraTicks, 3)` extra evenly-spaced ticks in the tail between the last data point and `domainEnd`, plus a tick exactly at `domainEnd` if its label isn't already present (`:527-550`), deduped by formatted label, sorted by x-position.
- Contrast: with NO brush (`xDomain == null`) and the domain still extended past data, bklit switches ALL ticks to `buildDomainTicks` (evenly-interpolated across the WHOLE domain, not data-aligned) — `:596-603`. So brush presence is itself the switch between "data-aligned + tail extras" vs "fully domain-interpolated" tick strategy.
- Migrated `internal/x-axis-overlay.tsx:49-65` already ports the no-brush `buildDomainTicks`-equivalent branch (comment cites `x-axis.tsx:597-603` exactly) — only the `xDomain != null` (brushed) branch (`appendProjectionTailTicks`) is missing.

## 3. Architecture for TanStack-native brush

### 3.1 Where selection state lives

Application-owned, per the audit. A new `internal/chart-brush.tsx` (or `use-brush-selection.ts` + `BrushOverlay` component pair) mirrors `ChartBrushLayout`'s ownership model exactly: a host-level `[brushSelection, setBrushSelection]` state (React `useState`, one level above the paired brush-strip chart + main chart — i.e. inside whatever new `BrushLayout` wrapper component the demo/consumer renders, NOT inside `line-chart.tsx`/`area-chart.tsx` themselves). `line-chart.tsx`/`area-chart.tsx` only ever receive `xDomain`/`xDomainSlotCount` as ordinary props, exactly as bklit's `LineChart`/`AreaChart` already do (§2.4) — **no new state lives inside the chart hosts**, only new prop-consumption of an existing-shaped domain/slot-count pair (`showcase/migrated/charts/line-chart.tsx`/`area-chart.tsx` do not currently accept `xDomain`/`xDomainSlotCount` at all — confirmed absent from both files' current prop surfaces; this is net-new plumbing, not a rewire of existing plumbing).

### 3.2 Definition-swap vs. domain-clamp — RECOMMENDATION: domain-clamp semantics, definition-swap mechanism, gated to commit-only

These are not actually alternatives at the TanStack-renderer level — per the doctrine fact given in the task brief ("marks groups `.ts-chart__marks` are RECREATED on any definition rebuild"), **any** change to `spec` (which is the sole input to `defineChart` → `definition`) triggers a full marks-group rebuild, regardless of whether the underlying `data`/`marks` array actually shrank. So "domain-clamp" (only remap the x-scale, keep the full array) does not avoid a definition rebuild in this renderer the way it might in a scale-only-update renderer — it only avoids CHANGING the marks array's size/identity. Recommend combining both ideas:

1. **Semantics: domain-clamp, matching bklit exactly (§2.4).** The `marks` builder for Line/Area always receives the FULL unfiltered dataset (bklit's `seriesSourceData = plotData` when `xDomain` is set) — never a `filterDataByXDomain`-shrunk array feeding the mark builder. Only the xScale's own domain narrows to `xDomain`, and only `yDomainTargetByAxis`-equivalent / interaction-data-equivalent consumers use a filtered slice internally (they don't feed `marks`). This preserves: inclusive-domain edge-fade pan-through behavior (fades stay anchored to the *viewport*, not to a shrinking data slice's own edges), and the `xDomainSlotCount`-driven column-width stability (§2.4) falls out naturally since nothing about column-width math needs `visiblePlotData.length` — reuse `data.length` (full) directly, no extra slot-count threading needed **for Line/Area specifically** (their bklit column-width usage is chiefly for marker/point sizing, not present on every host — verify per-host at dispatch).
   - Reasoning against literal `filterDataByXDomain`-then-rebuild: filtering would change the marks array's length/identity every commit, which is a strictly worse case for the "stable data-identity" doctrine (persistent per-row refs, future point-marker/projection features keyed by row index) than keeping the array constant and only reslicing what's *visible* via the scale mapping — same as bklit's own reasoning (§2.4 comment, verbatim).
2. **Mechanism: definition rebuild happens, but ONLY on brush COMMIT, never on intermediate drag frames.** This is the one deliberate, disclosed deviation from bklit (§3.3).

### 3.3 The drag-must-not-rebuild-the-definition mechanism (the pitfall the audit and task brief both flag)

bklit updates its caller's `xDomain` state on EVERY intermediate drag frame (`onChange`, §2.1) — acceptable in bklit because that only triggers a JSX-tree re-render (relatively cheap, no DOM node destroy/recreate). Doing the literal same against `line-chart.tsx`/`area-chart.tsx`'s `xDomain` prop would recompute `spec`/`definition` on every pointermove, destroying and rebuilding `.ts-chart__marks` (and everything single-writer-attached to nodes inside it) dozens of times per drag gesture — a direct doctrine violation.

**Proposed mechanism, with a working precedent already in this codebase**: `showcase/migrated/charts/internal/chart-selection.ts` (`useChartSelection`, 204 lines) already implements EXACTLY this shape of gesture for a different bklit feature (drag-to-select a "segment" range) — a `useEffect`-attached native `pointerdown`/`pointermove`/`pointerup` listener set (`:73-165`) that calls `setSelection(...)` (plain React `useState`, `:33`) on every pointermove, and `line-chart.tsx:920` renders the result via `<SegmentOverlay selection={chartSelection} .../>` as a **plain sibling SVG element passed alongside `<Chart definition={definition} .../>`, never as a `spec`/`marks` input** (confirmed: `chartSelection` does not appear in the `spec` `useMemo`'s dependency array at `line-chart.tsx:363`). This proves the "cheap per-pointermove React state driving an overlay outside `definition`" pattern is already safe and precedented in this exact renderer.

Recommended brush implementation mirrors it directly:
- **Preview (every pointermove during drag)**: a new `useBrushDrag`-style hook (co-located with the new brush chrome module, §4) tracks pixel extent + computed `{start,end}` Dates in local `useState`, used ONLY to position the three overlay layers (track fade, pattern fill, handle pills) — all rendered as plain React-portaled DOM (mirroring bklit's own portal-into-`containerRef` pattern, §2.2, which ALSO happens to be outside the SVG scene graph already, an easy 1:1 port for these three specific files' *visual* structure even though the underlying gesture math must be reimplemented). None of this preview state feeds `xDomain`/`xDomainSlotCount` props into the main chart.
- **Commit (pointerup / drag-end only)**: exactly once per gesture, call the `onSelectionChange`-equivalent that updates the `BrushLayout` owner's `brushSelection` state (§3.1), which is the ONLY point where the main chart's `xDomain` prop changes and `spec`/`definition` recompute — a single, discrete rebuild, the same cost class as any other prop change (e.g. changing `n`), not a per-frame cost.
- **Brush-strip chart itself never rebuilds during drag** — it is a static, once-built `LineChart`/`AreaChart` instance showing the FULL, un-brushed dataset (exactly like bklit's docs demos, §2's brush-strip render-prop) with `animate={false}`; the drag gesture's own overlay chrome is layered on top of it, independent of its `definition`.
- Reattachment across the (single, commit-triggered) definition rebuild on the MAIN chart follows the existing `hover-chrome.ts` precedent (`line-chart.tsx:515-521`): a `useEffect` keyed on the values that change post-commit (`renderData`/`xDataKey`/`xDomain`/etc.) calls `chromeRef.current?.reanchor()` rather than re-attaching from scratch — the brush-adjacent hover/tooltip chrome must gain `xDomain` to its own reanchor dependency list so a brush commit re-syncs tooltip/crosshair positioning (mirrors bklit's `use-chart-interaction.ts:314-323` re-anchor-on-brush-commit guard, §2.4).

**Open question flagged, not decided here**: whether "commit-only" (recommended) or an rAF-throttled intermediate commit (visually closer to bklit's live-pan, at a bounded 1-rebuild-per-frame cost) is the right call — see §9 Q4.
