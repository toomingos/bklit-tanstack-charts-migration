## Rulings (lead, made at plan time — log at approval)

1. **Native TanStack tooltip extension NOT adopted for visuals.** The bklit pixel mandate requires the exact `.bkm-tooltip-panel` DOM and bklit's flip-once-x + clamp-y positioning; TanStack's `placeTooltip` scores 4 placements with different edge/gap constants and would change pixels. The consolidated chrome stays imperative DOM driven by TanStack `focus` (public API — contract-clean). `renderTooltipBody`/`bodyChange` noted as a possible future adoption path, out of scope here.
2. **`spatialIndex`/`createGridPointIndex` adoption is OPTIONAL scope**, not tooltip parity: it is a focus-resolution perf option. Executor may wire `spatialIndex: createGridPointIndex` (import from the public package surface only) for scatter at n=100+ ONLY if trivially threaded; any m3c/m1c movement adjudicated at the bench gate. If not trivial, skip and note — no fork, no vendored-source edit.
3. **Liveline**: attempt consolidation onto the shared builders; if the D22 subtleties (sibling `boxCustom` island, live-axis pill ≠ DateTicker) make the shared path pixel-divergent, keep `live-hover-chrome.ts` consuming the shared BUILDERS (box/dot/crosshair constructors + tokens) while retaining its live-axis machinery — a documented composition, not a fork of the panel recipe.
4. **Out of scope**: pie/ring/funnel/heatmap/sankey/choropleth hover chromes (no tooltip box/crosshair/dot/pill — pure geometry hover effects; pie/ring/funnel already share `createPieHoverCoordinator`). D208-2 (pie hover dim) stays with initiative 5 per the register.
5. **Pie center**: migrated variant-grid was a deliberate no-React-in-hover-path design, but bklit renders `ChartStatFlow` (NumberFlow digit-roll) in the pie center. Deliverable D5 migrates pie's center VALUE DISPLAY onto `CenterStat` (the sanctioned island) keeping the coordinator-driven hover selection imperative — same recipe ring-center already uses. If a QA-visible regression appears, fall back to documented exception with PNG evidence.
