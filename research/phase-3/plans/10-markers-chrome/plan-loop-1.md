## 3. Architecture for TanStack-native port

### 3.1 `ChartMarkers`/`MarkerGroup` — application-owned overlay, NOT a `spec`/`marks` input

Per the established doctrine (cited in the 09 plan, `plan-loop-1.md:88`): "cheap per-pointermove React state driving an overlay outside `definition`" is precedented and safe (`internal/chart-selection.ts`). `ChartMarkers` is an even better fit for this pattern than brush, because bklit's OWN implementation is already React-portal-based with local `useState` fan/hover state (`marker-group.tsx:145-146`) — there is no gesture-timing hazard like brush's per-frame drag. Recommend porting `ChartMarkers`/`MarkerGroup` as a **plain React component tree**, registered as a new `CHART_ROLE` in `children.tsx` (mirrors `terminalMarker`/`brush` roles) so `<ChartMarkers items={...} />` can be passed as a host child, but rendered OUTSIDE the `spec`/`marks` `useMemo` — it only needs `xScale`, `innerHeight`, `margin`, `containerRef`, and read access to the SAME hover state `hover-chrome.ts` already owns (to compute `isActive` per date-bucket and to call `setTooltipData`-equivalent suppression). This does NOT require SVG-scene-graph marks at all; it is a sibling `<svg>`/portal layer exactly like `terminal-marker.tsx`'s `ProjectionMarkerOverlay` is already a sibling `<svg style="position:absolute;inset:0">` (`internal/terminal-marker.tsx:197`) — reuse that exact positioning idiom (translate by `margin.left,margin.top`) rather than visx-style in-SVG `<g transform>` composition, since the migrated tree has no visx dependency to lean on for the SVG-space math bklit used.

Fan-out portal target: bklit portals into `containerRef.current` (`marker-group.tsx:292-393`) — the migrated hosts already thread a `containerRef` for other portal chrome (brush, per init 9); reuse the same ref, do not create a second one.

Hover-hides-crosshair interaction (`chart-markers.tsx:103-111`, `setTooltipData(null)` on marker hover): the migrated equivalent is calling whatever `hover-chrome.ts` exposes to force-clear the active point (likely its `hide()`/blur path — verify exact method name at dispatch, `internal/hover-chrome.ts`'s public `HoverChrome` interface at `:85-90` exposes `onFocusGroupChange`/`reanchor`/`syncDim`/`detach`, none of which is an obvious "clear" — **may need a new small method or may already be reachable via `onFocusGroupChange([])`**; confirm at dispatch, don't invent a parallel clearing path).

### 3.2 `SeriesMarkers` persistent point-marker grid — reuse the `dot` mark exactly as Scatter already does

`showcase/migrated/charts/scatter-chart.tsx:1-16`'s own header comment documents the chosen architecture for a persistent point grid: **ONE `dot` mark per series** (`@tanstack/charts`' `dot()`, `showcase/repos/tanstack-charts/packages/charts-core/src/dot.ts:85-329`, resolved via the `@tanstack/charts/dot` → `charts-core/src/dot.ts` path alias, `showcase/tsconfig.json:68`), fill as a per-series radial gradient reproducing the fill-disc + gap + ring geometry in a single circle (halves per-point DOM node count vs. two-marks-per-series). This is the **exact same geometry** `MarkerCircles` computes in bklit (`series-point-marker.tsx:48-87`: inner fill + ring + optional outline) — **recommend Line/Area's `showMarkers` reuse this precedent literally**: when `showMarkers` is true on a `LineConfig`/`AreaConfig`, add a `dot(...)` mark to that series' contribution to the chart's marks array (spec-time, like every other mark), using the SAME radial-gradient-ring trick scatter-chart.tsx already built and already Q1/bench-approved. Do not build a second, React-portal-based point-grid renderer — that would duplicate an already-solved problem and add an unjustified second code path for the same visual primitive.

**Consequence**: toggling `showMarkers` becomes a `spec`/`marks`-array-shape change, i.e. a full definition rebuild — same cost class as any other structural prop toggle (adding/removing a `<Line>` child), not a per-frame cost, so no drag-style throttling concern applies here (unlike init 9's brush).
