# Radar Audit — migrated/charts/radar-chart.tsx

## 1. Summary
Migrated Radar uses stock `polar` + `radialArea` + `radialDot` + `angleGrid` (`migrated/charts/radar-chart.tsx:20`, `358-397`) plus TanStack-native `defineChart` → `<Chart>` with `focus:"nearest"` and `animate:true`, but grid and hover chrome are custom layers. The split is ~55% TanStack-native (polar marks + guides + host focus/animation lifecycle + `ChartSurface` sizing) vs ~45% custom (manual `ResizeObserver`, custom `bklitRadarGrid` `PolarGuide`, imperative `areaPathsRef`/`dotCirclesRef` + hover inline-style walk). Overall overhead verdict: **low-moderate and largely justified** — TanStack polar primitives already cover radar geometry; `bklitRadarGrid` half-step offset and lightweight hover walk are the only non-stock layers, both narrow in scope and close to removable.

## 6. Prioritized remediation candidates

1. **Drop manual `ResizeObserver` in favor of host sizing** — What to change: remove `useLayoutEffect` RO + `setMeasured` + `chartSize = fixedSize ?? min(width,height)` (`202-221`); use `fixedSize` as `<Chart width={fixedSize} height={fixedSize}>` when set, otherwise let host `ResizeObserver` own container and read `chartSize` from `onRender({scene})` `scene.width` (square via `aspectRatio:"1/1"` already on container). What it becomes: isomorphic sizing per `research/phase-2/tanstack-native/01-load.md` `currentWidth()`. Expected gain: **maint** (one sizing path) + **perf** (no duplicate RO). Risk: polar `scene.chart.width` may be narrower than container width due to auto margins; may need responsive `defineChart((ctx)=>spec)` builder reading `ctx.width`. Verification: screenshot square at 320/640 before/after; bench M1a stable.

2. **Eliminate `querySelectorAll` handle cache; drive hover via mark `id` → `scene`** — What to change: have `handleRender` capture `scene.nodes`/`scene.points` or store `chart:*` DOM element handles via `ChartRenderContext` instead of querying by `ts-chart__radial-area` class strings. What it becomes: className-agnostic hover targeting. Expected gain: **maint** (no host-internal class coupling) + **reliability** (survives hypothetical `ts-chart__` rename). Risk: requires storing `SceneNode` key→element map or switching to attribute-driven hover (e.g. data attribute set in mark `style` class). Verification: QA hover at 30/50/70 fractions passes if class renamed in test shim.

3. **Collapse imperative hover walk into host `onFocusChange` + CSS attribute selector** — What to change: emit `data-hovered="true"` / `data-dim="true"` attributes via `mark.style` mapping to `focusedPoint` state instead of `style.opacity`/`filter`/`transform` writes; move hover visuals to `styles.css` rules keyed on those attributes. What it becomes: no `areaPathsRef`/`dotCirclesRef`, no per-hover `style.*` loop, hover parity via CSS. Expected gain: **maint** (single CSS source) + **perf** (no per-hover JS style churn). Risk: TanStack mark `style` remap may require definition rebuild per hover (loses rAF-only benefit). Verification: bench M2 hover jank vs current imperative walk; QA glow/scale diff <0.5%.

4. **Wire `enterTransition`/`motionReplayKey` into host animation or drop stub props** — What to change: map `RadarEnterTransition {type,duration,ease,bounce,stiffness}` to `animate: {duration: enterTransition.duration ?? enterDurationMs, easing: bezierFromTransition(enterTransition)}` or document as ignored. What it becomes: either full API parity or explicit WONTFIX with JSDoc. Expected gain: **design** (API completeness per `research/phase-2/inventory/01-bklit-ui-inventory.md` §2.12). Risk: none. Verification: storybook `enterTransition={{type:"tween",duration:2000}}` visibly slower reveal.

5. **Retire `radar-spring.ts` dead import or give it a real narrow scope** — What to change: `radar-spring.ts` (`49` lines `estimateSpringSettleMs`/`sampleSpringProgress`) exported but never imported by `radar-chart.tsx` after lightweight hover walk replaced spring chrome (`radar-chart.tsx` imports only `bklitRadarGrid` from `radar-reveal.ts`). Either delete `radar-spring.ts` or reuse for grid-entrance stagger if reintroduced. What it becomes: no dead code. Expected gain: **maint** (remove misleading file). Risk: other charts (`pie`/`ring`/`gauge`/`funnel`) use sibling `candle-spring.ts`/`spring.ts` — verify no cross-import. Verification: build still passes; no import graph reference to `radar-spring.ts` remains.

6. **Fix stale-hover after series-count change** — What to change: add `resolvedAreas.length` to hover `useLayoutEffect` deps or second effect that repaints hover immediately when `handleRender` refreshed `areaPathsRef`. What it becomes: new polygon appears at correct opacity without extra pointer move. Expected gain: **design** (no one-frame empty polygon). Risk: extra paint on data-shape change only. Verification: QA inject `data.push(newSeries)` at `hoveredIndex=1` → new polygon dimmed appropriately without move.
