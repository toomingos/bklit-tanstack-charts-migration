# Composed Audit — migrated/charts/composed-chart.tsx

## 1. Summary
Migrated Composed combines stock `lineY` per line (`migrated/charts/composed-chart.tsx:482-493`) with two custom marks — `areaFill` (`migrated/charts/internal/area-fill-mark.ts:27`) and `seriesBarMark` (`migrated/charts/internal/series-bar-mark.ts:45`) — inside one `defineChart` → `<Chart>` lifecycle, but sizing, scales, axes, hover, and double reveal are all custom layers. The split is ~25% TanStack-native (mixed-mark `ChartSpec.marks` grammar + keyed reconcile) vs ~75% custom imperative chrome (30-line custom bar geometry, dual-decimation data paths, HTML `XAxisOverlay`, native bisector hover, WAAPI clip+per-bar stagger). Overall overhead verdict: **high but largely justified** — `seriesBarMark` width/math and `areaFill` heap fixes are deliberate parity/performance choices, while custom `ChartScale` stashing, `XAxisOverlay`, and hover bypass duplicate stock TanStack `focus`/`animate`/`guides` at measurable maintenance cost.

## 6. Prioritized remediation candidates

1. **Replace double WAAPI reveal with single host `animate` + per-bar stagger via CSS `animation-delay`** — What to change: keep `clipPath` wipe but move bar stagger from `handleRender` DOM walk (`779-805` per `resolvedBars×data.length` `rect.animate`) to declarative `animation-delay` driven by data index or TanStack `revealTiming`. What it becomes: no `querySelector` per mount, no `revealAnimationsRef` array, deadline `cancel()` guarded by `clearTimeout` handle stored in ref. Expected gain: **perf** (no `Animation` per bar rect; M1a mount avoids `rAF×2+setTimeout(0)` setup + `getAttribute` snapshot race) + **maint** (single reveal path, `deferred-reveal.ts:onPostPaint` reused). Risk: CSS `animation-delay` on SVG `rect` `height` may not hardware-accelerate same as WAAPI `height`. Verification: bench M1a at `data.length=100` before/after; QA settled pixel diff at 1.1s clip boundary.

2. **Wire `xScaleD3Ref`/`yScaleD3Ref` via responsive `defineChart((ctx)=>spec)` builder** — What to change: derive `xScaleD3Ref`/`yScaleD3Ref` from spec builder `ctx.range`/`ctx.tickCount` (host `ChartBuildContext` `width/height/theme`) instead of manual `ChartScale.resolve` stashing; have `xForIndex` read `scene.scales` supplied via `onRender({scene})`. What it becomes: scales always range-correct after resize, no stale-ref race; `hoverInputsRef` dual-path collapsible to host `ChartPoint`s. Expected gain: **design** (highlight band never drifts) + **maint** (removes 70-line `ChartScale` wrapper). Risk: builder form may invalidate identity memoization each render. Verification: QA hover band at `width=320` vs `960` cross-checked vs bklit; resize-drag bench stable.

3. **Adopt host `focus` for hover and retain chrome as `renderTooltipBody` portal** — What to change: set `defineChart({focus:'group-x', tooltip:{className,anchor:'point'}})` and have `attachHoverChrome` consume `onFocusGroupChange` points (drop manual `bisectDateLeft`/`resolveNearestIndex` + dual index). What it becomes: `handleFocusGroupChange` maps `ChartPoint`s to `chrome.onFocusGroupChange` with `rawIndex` unified to `datumIndex` (collapsing dual-index hazard). Expected gain: **maint** (single hookup, no SVG discovery) + **perf** (host reuses `spatialIndex` when `n>1000`). Risk: host grouped `x` may collapse bar `yValue` points sharing same time — need `custom ChartFocusStrategy` to preserve per-series `barRowIndex` semantics. Verification: QA hover fractions at `n=100/1000` vs bklit; bench M2 hover jank unchanged.

4. **Move gradient defs to `defineChart({gradients})` via `renderChartSvgWithResources`** — What to change: move area gradient `linearGradient` array into spec `gradients` field so `renderChartSvgWithResources` scopes `idPrefix` via `useId`, instead of sibling 0×0 `<svg>` `url(#id)` document-wide resolution. What it becomes: `gradients` array passed to `defineChart`, `fill: url(#gradId)` refs remain. Expected gain: **design** (ID scoping via `idPrefix` per `research/phase-2/tanstack-native/01-load.md` §Theme/margin) + **maint** (no DOM-order fragility with QA harness `first <svg>` assumption).
