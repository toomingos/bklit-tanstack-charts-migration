# Bar Audit — migrated/charts/bar-chart.tsx

## 1. Summary
Migrated Bar is vertical, grouped-only (no stacked/horizontal/perspective/squares) and reuses stock `barY` per series with a nested `groupScale` band plus fully TanStack-native `defineChart` → `<Chart>` spec — the one chart where the mark layer itself is largely stock. However sizing, hover hit-testing, axes, and reveal are all custom parallel implementations that duplicate work TanStack already does. The split is ~35% TanStack-native (marks + reconcile) vs ~65% custom (margin-inclusive `scaleBand`/`scaleLinear` rebuild, band-index pointermove, `BarXAxisOverlay`, WAAPI per-rect reveal, per-category dim). Overall overhead verdict: **moderate-high** — stock `barY` is correct, but the surrounding hover/reveal/axis layers are the heaviest retained bklit parity cost at demo scale and the richest remediation surface among the four charts.

## 6. Prioritized remediation candidates

1. **Replace band-index hover with TanStack `focus: 'group-x'`** — What to change: remove native `pointermove` listener + `hoverInputsRef` band division; set `defineChart({ focus: 'group-x', tooltip: true, maxFocusDistance: Infinity })` and wire `attachBarHoverChrome` to `onFocusGroupChange` using `ChartPoint.group`/`xValue` (category label) and `ChartPoint.y`/markId for per-series bar centers. What it becomes: one `focus` strategy, no parallel `categoryScale`/`columnWidth` math outside TanStack. Expected gain: **maint** (remove 70-line pointer handler + RO drift) + **perf** (no per-move `getBoundingClientRect` + `querySelector`). Risk: TanStack `group-x` groups by semantic `xValue` (category string) — must verify grouping collocates all `barY` points sharing same categoryLabel exactly as `Math.floor(pos/columnWidth)` does; padding-induced label mismatch (see §4 columnWidth bug) would surface. Verification: QA hover-30/50/70 tooltip row values at n=100 vs bklit; bench M2 pointermove frame cost.

2. **Switch WAAPI per-rect reveal to `animate:true` or single `clipPath` tween** — What to change: drop per-`rect` `animate([{height:0}→{height}])` loop (one `Animation` per bar); use `animate: { duration: animationDuration, easing: 'easeInOut' }` and let `reconcileChartSvg` interpolate `height`/`y` via `interpolatedAttributes` (`height,y` are in the list — `research/phase-2/tanstack-native/02-render.md` §reconcile `interpolatedAttributes`), or single `clipPath inset` on `.ts-chart__marks`. What it becomes: ~5 lines vs 65-line `handleRender`. Expected gain: **perf** (no `Animation` allocation storm; deferred `onPostPaint` dance removed) + **maint** (shared pattern with scatter/area). Risk: loses per-bar stagger (`staggerSpread 0.4*animationDuration`); if stagger is design-required, keep WAAPI but gate to pilot `animationDuration=1100` only. Verification: bench M1a at n=100 and n=1000 (if bench ever scales bar); QA settled screenshot diff <0.5%.

3. **Collapse `BarHoverChrome` duplication into shared `hover-chrome.ts`** — What to change: share crosshair/dot/box/pill/label-fade springs + `createSpring` + gradient defs via shared helper; keep only `setCategoryHover` per-category dim as bar-specific override. What it becomes: `import { createHoverChromeBase } from './hover-chrome-base'` instead of 455-line copy (comment `bar-hover-chrome.ts:1-7` admits copy). Expected gain: **maint** (fix spring constants in one place, not three). Risk: proven charts regress if shared helper diverges; keep copy until shared helper extracted. Verification: QA hover captures unchanged; unit test dim opacity still 0.3.

4. **Remove parallel `categoryScale`/`valueScale` reconstruction; pass factories to TanStack** — What to change: pass `scaleBand().domain(categories).padding(barGap)` factory (not instance) as `x.scale` and `scaleLinear().domain([0,max*1.1]).nice()` factory as `y.scale`; read back ranged scales via `onRender` `scene.scales` for hover dot y instead of local `valueScale`. What it becomes: TanStack owns range application; no manual `Math.round(width/aspectRatio)` height calc. Expected gain: **maint** + **design** (single source of range truth; fixes §4 height NaN and padding drift). Risk: `groupScale` still needs local `bandWidth` to derive `paddingInner`; keep local band calc until groupScale folded. Verification: screenshot band positions unchanged; hover dot y pixel identical.

5. **Consolidate sizing to `<Chart width/height/aspectRatio>` and delete manual ResizeObserver** — What to change: accept optional `width` prop; otherwise let `<Chart>` measure via its own `ResizeObserver` and derive `innerWidth` from reported size in `onRender` or responsive `defineChart((ctx)=>spec)`. What it becomes: isomorphic SSR path (`research/phase-2/tanstack-native/01-load.md` §SSR `initialMarkup` `prerender()`). Expected gain: **perf** (one RO, not two) + **design** (SSR markup). Risk: need responsive builder to keep `categoryScale` domain stable across size changes. Verification: bench M1a first-paint without client RO tick.

6. **Throttle per-move `setCategoryHover` or gate to `requestAnimationFrame`** — What to change: wrap `setCategoryHover` writes in `requestAnimationFrame` coalescing (or skip if `hoveredIndex` unchanged). What it becomes: at most one `O(n)` dim pass per frame, not per `pointermove` event. Expected gain: **perf** (caps 2k writes/frame at n=1000). Risk: minimal — bklit already rAF-dedupes via `use-scheduled-tooltip.ts` (`research/phase-2/bklitui-native/03-hooks-and-updates.md` §rAF deduped tooltip). Verification: bench pointermove 60fps at n=1000 stays <16ms.
