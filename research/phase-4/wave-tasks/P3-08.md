## Part A — T-D6: findNearestPoint replaces resolveNearestIndex/bisect

### What the swap actually is

`resolveNearestIndex` and `bisectDateLeft` both live in **one 38-line file**, `internal/bisect.ts:1-38` (not two files as tanstack.md's phrasing might suggest): `bisectDateLeft` (lines 2-16, leftmost binary search) and `resolveNearestIndex` (23-38, bisects then applies a strict-`>` tie-break toward the earlier point, matching bklit's `resolveTooltipFromX`). Native `findNearestPoint` (scene-level API) is the replacement target.

Consumers, all via `import { resolveNearestIndex } from "./internal/bisect"` or the barrel:
- `composed-chart.tsx:125` (import), `:1172` (`rawIndex = resolveNearestIndex(rawRows, ...)`), `:1178` (`decimatedIndex = resolveNearestIndex(decimatedRows, ...)`)
- `internal/chart-selection.ts:4` (import), `:56` (generic selection resolver)
- `internal/index.ts:6` re-exports both
- Candlestick and scatter reference the same semantics in comments (`candlestick-chart.tsx:28`, `internal/candlestick-focus-strategy.ts:2`, `internal/scatter-focus-strategy.ts:30`) but route through their own focus-strategy files rather than calling `resolveNearestIndex` directly — check those focus-strategy files for their own bisect logic before assuming composed is the only consumer.

### What explicitly STAYS custom

**Composed's dual-index split must not be collapsed.** `composed-chart.tsx:1172-1202`: bars render **raw** `data` (comment at line 803: "bklit quirk: not decimated") while line/area render `renderData` (LTTB-decimated, line 1148: `renderData: decimatedRows`). On hover, composed resolves the pointer x against **both** arrays independently — `rawIndex` against `rawRows` (line 1172) and `decimatedIndex` against `decimatedRows` (line 1178) — then uses `decimatedIndex >= 0 ? decimatedIndex : rawIndex` as the point's `datumIndex` (line 1196) for line/area rendering, while feeding `rawIndex` to the bar chrome (`chromeRef.current?.onFocusGroupChange(points, rawIndex)`, line 1202). This split exists because bars and lines/areas in one composed chart are keyed to **different-length arrays** post-decimation — one nearest-point resolution cannot serve both. `findNearestPoint` (native, single-array) can replace each individual bisect *call*, but not the dual-resolution architecture itself. Do not "simplify" this into one shared native call.
