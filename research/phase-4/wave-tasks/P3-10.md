## What explicitly STAYS custom — this is the most over-claimed row in tanstack.md; read carefully

**Contradiction: `fade-mask.ts` does NOT qualify as a native-swap candidate at all, despite tanstack.md row 5 crediting it ~190 LOC of payoff and listing `internal-animation (fade-mask)` among the ★ full-native parts.** Verified by reading the whole 190-line file:

- `viewportFadeGradientAttrs(innerWidth)` (`fade-mask.ts:64-72`) returns `gradientUnits: "userSpaceOnUse", x1: 0, x2: innerWidth, y1: 0, y2: 0` — this is literally the pattern go-to-plan's own no-native-path table names as unsupported ("userSpaceOnUse gradient coords — %-coords only, frozen at definition"). This feeds **both** the crosshair/indicator fade (`indicatorFadeGradientStops`/`crosshairFadeStops`, lines 104-145) **and** the real profit-loss (PL) fade consumer, traced to `line-chart.tsx:1085`: `<linearGradient gradientUnits="userSpaceOnUse" x1={0} x2={g.endX} y1={0} y2={0}>` (built at `line-chart.tsx:915-922` via `resolveProfitLossGradientDefs`, imported from `internal/profit-loss-line-mark.ts`). Both halves are `userSpaceOnUse` — both must stay custom.
- The **other** half of the same file — the line/area **edge-fade** mask — is not an SVG gradient at all. The comment at `fade-mask.ts:11-14` states it's applied via CSS `mask-image` in `styles.css`; `resolveFadeEdgesMask` (lines 179-190) only computes `data-bkm-fade-edges*` boolean attributes, not gradient defs.

**Neither half of `fade-mask.ts` is a valid native-swap target for this package. Drop it from scope entirely — do not touch this file, and do not count it toward this package's LOC payoff or completion criteria.**
