### Cross-reference constraint — D258 ring oscillation (read in full before touching ring)

D255 originally ruled ring's enter/leave-on-springing-group structure an ACCEPT (bklit has the identical binding shape, `ring.tsx:179-188` ↔ `ring-chart.tsx:725`/`ring-hover-chrome.ts` — **note: the transform-application code that D258 cited at `ring-hover-chrome.ts:104` now sits at `:108` on current disk** (`applyTransform`'s `config.trackGroupEl.style.transform = value` block) — a small line-drift, re-locate before citing). **D258 (2026-08-24) overturned that ruling with direct measurement: ring is a genuine defect** — at the mandated n=1000, migrated's hover spring never settles (38 distinct transform signatures still cycling in the final second) while bklit settles deterministically at `at=0`. Do not re-derive this from scratch; three explicit constraints carry forward into this package unchanged:

1. **The prescribed fix (binding hover listeners to an unscaled wrapper `<g>` around track+progress) addresses the oscillation mechanism only.** It does **not** address a second, separate, still-open finding: at n=4 (the most realistic density, where no oscillation occurs on either side), bklit acquires hover during the harness's fly-in animation and retains it while resting in the ring's centre hole, but migrated ends completely flat (no hover state at all). This acquisition/retention gap is unruled and out of this package's scope — do not attempt to fix it here, and do not let a "ring passes at n=1000/100 now" result be read as closing this gap too.
2. **Migrated's hover-wiring style stamps (`cursor`, `transformOrigin`, `pointerEvents:"none"`) read empty on the live DOM despite their listeners firing** — TanStack appears to rewrite the style attribute after the wiring effect runs. This is routed to **P4.3**, not this package. Do not attempt to fix it here; if your `createChartSpring` swap happens to touch this wiring, preserve the existing (broken-but-out-of-scope) behavior rather than incidentally fixing or worsening it, and report if you can't avoid touching it.
3. **Do not re-investigate pivot semantics.** D258 measured and ruled out a pivot-origin mismatch as the cause — both bklit (via Framer's fill-box `50% 50%` resolving to per-ring absolute centres) and migrated (`dx = −dw/2, dy = −dh/2` exactly) pivot about each ring's own centre. This is settled; do not re-derive it.

**This package's ring gate must include hover captures, not settled-only** — a settled-only gate is blind to an oscillation defect by construction (this is the same risk class as the sunburst reveal-replay invariant documented in `P3-06.md` and sankey's label-slide timing in `P3-07.md`: a mechanism that only manifests mid-animation is invisible to a post-settle diff).

## Part B — Host-sizing adoption audit (`tanstack 9` ruling)

### What the audit actually is

go-to-plan.md:56 (`tanstack 9`): *"Keep `use-container-size` family; adopt host sizing only where no HTML overlay needs a rect (audit inside T-D10); add `onRender`-fed rect only if it removes ≥2 hooks."* This is explicitly **not** a mandate to delete `use-container-size.ts` — it's an audit to find which of its consumers can be migrated to `<Chart aspectRatio width>`'s native host-sizing, keeping the file itself as a compensating layer for whichever consumers still need a raw rect for an HTML overlay.

**Verified directly, current disk: 14 consumer files** (not fewer) — matching `tanstack.md` row 23's own stated "14 parts" exactly, via the five hook variants in `internal/use-container-size.ts` (225 lines):
- `useContainerWidth`: bar-chart, choropleth-chart, candlestick-chart, scatter-chart (4)
- `useDebouncedContainerWidth`: composed-chart, gauge (2)
- `useDebouncedContainerSize`: gauge, line-chart (2, gauge uses both this and the width variant)
- `useMeasuredRect`: area-chart, pie-chart, radar-chart, live-line-chart, ring-chart (5)
- `usePositiveChartSize`: heatmap-chart, funnel-chart (2)

Unique files: bar, choropleth, candlestick, scatter, composed, gauge, line, area, pie, radar, live-line, ring, heatmap, funnel = **14**. Confirmed `sunburst-chart.tsx` and `sankey-chart.tsx` have **zero** references to any of these five hooks — they are not part of this audit's scope.

**Note on a discrepancy in prior working notes for this package: an earlier pass on this research recorded "13, not tanstack.md's claimed 14" as a finding. That count does not reproduce on a fresh direct grep this round — the count is 14, matching tanstack.md exactly. Treat "14" as the current verified figure; if you find a reason the true consumer count is 13 (e.g. one file re-exporting rather than truly consuming, or one hook call being dead/unreachable code), report exactly which file and why, since this contradicts a previous pass.**

### What explicitly STAYS custom

Per the `tanstack 9` ruling's own text: any of the 14 parts whose rect is consumed by an **HTML overlay** (not just internal layout math) must keep a thin rect hook, even after adopting native host sizing elsewhere in the same component — native `<Chart>` sizing does not expose a rect to sibling HTML DOM. Build the per-part table required in Report back (below) identifying, for each of the 14, whether its size hook feeds only internal SVG/scale math (adoption candidate) or also an HTML overlay (must keep the rect hook regardless of what else changes). Two parts are flagged as the most likely consolidation candidates based on their generally HTML-overlay-heavy chrome: **radar** and **gauge** — verify rather than assume.
