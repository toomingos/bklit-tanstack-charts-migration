## Part B — T-D11: Hover dim → mark `states when:{focus:'unmatched'}`

### What the swap actually is

`go-to-plan.md:129`: *"Hover dim → mark `states when:{focus:'unmatched'}` (opacity dims only; blur/scale stay custom)."* **Verified: zero existing usages of `states`/`when:{focus:...}` anywhere in `showcase/migrated/charts` today** — this task is fully greenfield, unlike Part A. The current mechanism is `internal/hover-chrome.ts`'s `attachHoverChrome(options)`, whose `dimOpacity` option (`hover-chrome.ts:104`, `dimOpacity?: string`, default `DIM_OPACITY = "0.3"` at line 35) is applied imperatively via `element.style.opacity = dimOpacity` at multiple call sites (lines 374, 376, 381, 383, 387, 423, 434, 639, 650) across the dimmed (non-hovered) series' paths/fills/dash-tails.

Native target: the vendored `states` array shape, confirmed directly from `charts-core`'s own test suite (`focus-mark.test.ts:800-803`): a mark can carry `states: [{ when: { focus: 'unmatched' }, style: { opacity: 0.2 } }]` — an array of declarative state-rules, each gated by a `when` matcher and applying a `style` object. This is a **per-mark** config (the `states` field is typed at `types.ts:1048,1067,1302`, attached to individual mark definitions, not globally) — meaning each mark type in a chart can carry its own distinct dim-opacity value.

### Cross-reference constraint — C11 fix folds directly into this package's acceptance criteria

`go-to-plan.md:199,217`: *"C11 composed per-series `dimOpacity` (area 0.6 / line 0.3 vs chart-wide 0.3)... FIX — composed dims per-series (area 0.6/line 0.3), not chart-wide. **Because native `states` is per-mark, this swap is a natural fit for fixing C11, not an extra burden**: give composed's Area mark its own `states: [{when:{focus:'unmatched'}, style:{opacity:0.6}}]` and its Line mark its own `states: [{when:{focus:'unmatched'}, style:{opacity:0.3}}]`, matching bklit's per-series values exactly instead of `attachHoverChrome`'s current single chart-wide value. **This package's acceptance criteria explicitly include verifying composed's dim now differs correctly between its Area and Line marks** — do not treat this as merely "swap the mechanism and keep whatever single value was already there"; verify the actual dimmed-opacity output differs per mark type in composed post-swap.
