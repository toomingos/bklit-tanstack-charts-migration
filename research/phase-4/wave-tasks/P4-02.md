## Scope

Three strands.

### Strand 1 — T-C2: focus-strategy kit

Three `internal/*-focus-strategy.ts` modules implement `ChartFocusStrategy<ChartDatum, XType, YType>` (`resolve`/`group`/`navigation`) to replicate bklit's exact hover/focus targeting math atop TanStack's native focus system:

- `internal/bar-focus-strategy.ts` (166 lines) — `valueKey` (line 5, string-keyed generic Date/other), `collectPerGroup` (line 10, **sorts `others` by `a.y - b.y`**), `createBarFocusStrategy` (line 42) with dual-mode `resolve`: exact bklit band-division math when `getCategoryOrder`/`getInnerWidth` getters are supplied, else nearest-band-center fallback. `group` (146) delegates to `collectPerGroup`. `navigation` (154) sorts x→y then dedupes by xValue.
- `internal/scatter-focus-strategy.ts` (86 lines) — `valueKey` (line 5, **byte-identical to bar's**), `collectPerMark` (line 10, same y-sort pattern as bar's `collectPerGroup`), `createScatterFocusStrategy` (line 44), single-mode nearest-x resolve. `group`/`navigation` mirror bar's shape.
- `internal/candlestick-focus-strategy.ts` (81 lines) — **genuine behavioral divergence, not just a different name.** Uses `epochMs(value: unknown): number` (line 18, Date-only, returns `NaN` for non-Date) instead of `valueKey`. Inlines its own group-collection `Map` logic directly inside `resolve` (27-52) and `group` (54-67) **without** sorting by y — `return [...unique.values()]` at line ~66 preserves Map insertion order only, unlike bar/scatter's explicit y-sort. `navigation` (69-79) is shape-identical to bar/scatter's but keyed by `epochMs`.

Before unifying into one kit: **the y-sort omission in candlestick's `group` is either an intentional per-chart difference (candlestick's group semantics may not need y-ordering) or a latent bug bklit itself has/lacks.** Check the legacy bklit source (`repos/bklit-ui/`) for candlestick's actual grouped-tooltip ordering before deciding whether to (a) extract a shared `collectPerGroup`-style helper and make candlestick opt into y-sort, matching bar/scatter, or (b) keep candlestick's insertion-order behavior as a documented, deliberate divergence inside the shared kit (e.g. a `sortGroup` flag). Do not silently normalize candlestick to y-sorted order without confirming that's what bklit does — that would be a behavior change disguised as a refactor.

`valueKey` (bar/scatter, byte-identical) is a safe, low-risk shared extraction regardless of the above.

### Strand 2 — T-C7: `createBroadcastStore<T>`

This is a **generic extraction over existing per-chart broadcast stores** (get/set/subscribe coordinators for imperative hover-state fan-out without full React re-renders), not new functionality. Concrete stores it must subsume:

- `internal/pie-hover-chrome.ts` — `PieHoverCoordinator` interface, `createPieHoverCoordinator(onHoverChange, isControlled)` (lines 65-101): `getHovered`, `requestHover` (controlled/uncontrolled dispatch, **no dedup check**), `requestUnhover`, `setHovered` (imperative, **no dedup**), `subscribe`/`notify` via `Set<listener>`. Importers confirmed via grep beyond its own file: `pie-chart.tsx`, `internal/ring-hover-chrome.ts`, `internal/funnel-hover-chrome.ts` — **already generic/reused by 3 chart parts**, single hovered-index shape.
- `internal/heatmap-hover-chrome.ts` — `HeatmapHoverCoordinator` interface (48-61), `createHeatmapHoverCoordinator()` (63-106). Tracks **three** pieces of state (`hoveredCell`, `hoveredLegendLevel`, `tooltipData`) instead of one. **Every setter has an equality-check dedup guard before notify** (lines 75-93: `setHoveredCell`/`setHoveredLegendLevel`/`setTooltipData` each early-return on unchanged value) — this is a real behavioral difference from pie's coordinator, which has none. Importers: `heatmap-chart.tsx`, `internal/heatmap-interaction.tsx`.

**The generic `createBroadcastStore<T>` must preserve heatmap's dedup-guard behavior** (either as a built-in equality check the generic store always does, or as an opt-in comparator param) — do not regress heatmap to pie's no-dedup behavior, and do not force pie into heatmap's guard behavior without checking whether pie's callers rely on being notified even on same-value re-hover (its own `requestHover`/`setHovered` currently have no guard — that absence may be load-bearing for its controlled-mode re-dispatch semantics; verify against bklit's pie hover behavior before changing it).

### Strand 3 — T-C8: bar-squares math consolidation

`bandWidthForSquares(bandWidth, seriesCount, groupGap)` is duplicated **byte-identical** in two modules:

```ts
function bandWidthForSquares(bandWidth: number, seriesCount: number, groupGap: number): number {
  if (!bandWidth || seriesCount === 0) return 0;
  const effectiveGroupGap = seriesCount > 1 ? groupGap : 0;
  return (bandWidth - effectiveGroupGap * (seriesCount - 1)) / seriesCount;
}
```
at `internal/bar-column-track-mark.ts:23-27` and `internal/bar-squares-mark.ts:28-32`.

Move it into `internal/bar-squares-layout.ts` — the natural target module (currently 90 lines, exports `computeSquareColumn` at 16-63 and `topSquareCenterY` at 65-89, does **not** yet contain `bandWidthForSquares`) — and have both call sites import from there.

Only the two byte-identical module-level copies above exist; don't go hunting for a third that isn't there.
