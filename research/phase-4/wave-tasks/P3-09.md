## What the swap actually is

`go-to-plan.md:126`: *"Native tooltip cutover per-part (placement/offset/motion/portal); pill/date-pill/square-ring/fade-gradient stay custom; retire scheduler + box halves per part only when that part's pixel gate passes."* Native target: the `tooltip` field on `ChartDefinitionOptions` (`showcase/repos/tanstack-charts/packages/charts-core/src/types.ts:1429-1457`, `ChartTooltipOptions`), which provides `placement: 'auto' | ChartTooltipPlacement | readonly ChartTooltipPlacement[]`, `offset: number`, `motion: false | ChartMotionTransition`, `portal: ChartTooltipPortalInput`, and `content`/`format`/`formatGroup` for tooltip body rendering.

**Confirmed this is fully greenfield across all six parts**: a direct grep of `bar-chart.tsx`, `scatter-chart.tsx`, `candlestick-chart.tsx`, `live-line-chart.tsx`, `heatmap-chart.tsx`, `choropleth-chart.tsx` for a native `tooltip:`/`tooltip: {` config inside their `defineChart` calls returns **zero hits** in every one. What each of these six files actually has, named `tooltip`, is an app-supplied `<ChartTooltip>` **JSX child** extracted via `CHART_ROLE`/`extractChildren` composition (confirmed at `bar-chart.tsx:183`, `tooltip` destructured from the same `React.useMemo(...)` child-classification block that produces `bars`/`grid`/`xAxis`/etc.) — a config *object*, not the native `defineChart` tooltip option. Everything downstream of that (`tooltipEnabled = tooltip?.enabled ?? false` at `bar-chart.tsx:663`, the `attachHoverChrome`-driven imperative DOM machinery) is bklit-parity hand-rolled chrome. **None of the six parts uses the native `tooltip` option at all today; this package introduces it from scratch, one part at a time.**

The shared machinery each part currently drives:
- `internal/tooltip-chrome.ts` (624 lines — close to but not exactly tanstack.md row 19's cited 632; re-measure at dispatch time since this file may have moved since) — `buildIndicator`/`positionIndicator` (crosshair line, lines 109-201), `buildDotLayer`/`ensureDot`/`updateDotPosition`/`hideDot` (focus dots, 203-316), `buildBox`/`positionBox`/`applyBoxContent`/`hideBoxContent` (the tooltip panel itself — placement/flip/content, 317-517), `createDateTicker` (518-585), `buildPill`/`applyLabelFade`/`resetLabelFade` (the date-pill, 586-624).
- `internal/tooltip-scheduler.ts` (67 lines, exact match to tanstack.md's citation) — `createTooltipScheduler`, a `requestAnimationFrame`-batched dedupe/commit scheduler (`schedule`/`clear`/`resetDedupe`/`dispose`) sitting in front of whichever `commit` callback each part wires up. This is the piece most likely to retire once a part's tooltip commit path moves fully onto native scheduling — but only for parts where it's confirmed unused post-swap, and only after that part's own gate passes (per the sub-run ordering above).
- Five per-part `*-hover-chrome.ts` modules, each cloning/adapting `tooltip-chrome.ts`'s mapper functions for their own chart's geometry: `bar-hover-chrome.ts` (452 lines), `scatter-hover-chrome.ts` (369), `candlestick-hover-chrome.ts` (377), `live-hover-chrome.ts` (398), `heatmap-hover-chrome.ts` (139). **Choropleth has no `choropleth-hover-chrome.ts` file of that exact name in the standard set — verify the actual filename for choropleth's chrome at dispatch time** (a file named `choropleth-hover-chrome.ts`, 348 lines, was found this round, but confirm it's still current and holds the same role as the other five before treating it as directly parallel).
