## Read this scope clarification before doing anything else

T-D1's acceptance criterion is **"zero pixel drift on reveal gates."** That is a conservative bar. It does **not** require rearchitecting these charts' reveal animations onto native TanStack marks driven by `motion()`. Verified from the clone at HEAD (`showcase/repos/tanstack-charts/packages/charts-core/src/motion.ts:207,209`):

```ts
const defaultDuration = 1_100
const defaultStaggerRatio = 0.4
const defaultEasing = cubicBezier(0.85, 0, 0.15, 1)
```

These are **module-private** constants (not exported) — the exported surface is `export function motion(options?: ChartMotionOptions)` (line 754), which applies these defaults internally when a caller omits `duration`/`easing`. There is no way to *import* `1_100`/`cubicBezier(0.85,0,0.15,1)` as named constants from the native package; the only way to "consume the native default" is to invoke `motion()` itself with those fields omitted, on a mark that actually goes through TanStack's own scene/motion pipeline.

The seven parts in scope render their reveal animations as **hand-rolled WAAPI `.animate()` calls on custom SVG attributes** (pie wedge sweep angle, ring stroke-dasharray, funnel `scale(...)`, radar polygon points, line/area/composed `d`/opacity), not as native TanStack marks. `internal/enter-transition.ts`'s own extensive header comments explain why this machinery exists and must stay (see below) — including a documented empirical finding (D51) that a native two-keyframe tween cannot correctly animate SVG `d`/path attributes at all (CSS `d` interpolation is discrete between mismatched path structures). **Do not attempt to move these charts onto native `motion()`-driven marks as part of this package** — that is a much larger re-architecture than the acceptance bar requires, and risks reintroducing exactly the bug D51 already found and fixed around. The correct scope is narrower: stop hand-copying `1100`/`cubic-bezier(0.85,0,0.15,1)` as local literals in `internal/design-tokens.ts`, and instead make `TWEEN_FALLBACK`'s two fields track the native default (e.g. by calling `motion()` with no duration/easing once, at module scope, purely to read back its resolved defaults if the API exposes them that way — or, if it does not expose a read-back path, document that and keep the literals with a comment tying them explicitly to `motion.ts:207,209` as the source of truth). **If your investigation shows there is no clean way to read the native default without invoking the full `motion()` pipeline, say so explicitly and propose the narrowest faithful alternative — do not silently rewrite the reveal engine.**

## What explicitly STAYS custom

**The entire surrounding engine in `internal/enter-transition.ts` stays.** This is the most likely source of over-deletion for this package — read the file's own header comments (lines 1-36, 130-160) before touching anything:
- `resolveEnterTransition` (87-128) — resolves a caller-supplied `EnterTransition` (framer-style `{ease:[...]} | {bounce|stiffness,damping}`) against a fallback; both the spring-bounce conversion (`springFromBounce`, 71-79, bklit's verbatim `springOptionsFromTransition` formula) and the tween-duration/easing resolution logic have no native equivalent to delegate to.
- `revealTiming` (166-183) — produces a `RevealTiming` with `sampledProgress`: for tweens, 64 **uniform** progress samples (`TWEEN_SAMPLES = 64`, lines 160-164) fed through the cubic-bezier as the WAAPI *timing-level* easing, not the keyframe-level values — this exact approach is required per the file's own comment (144-150) because CSS `d`/path interpolation is **discrete** between structurally-mismatched paths (empirically verified, D51) and a plain 2-keyframe animation would visibly snap instead of sweep.
- `buildProgressKeyframes` (187-192) — maps `sampledProgress` through a per-chart `toKeyframe` callback (e.g. pie's wedge-angle keyframe builder, ring's dasharray builder). This callback family is itself per-chart custom code and stays.
- **Gauge's own default fallback is a spring, not the 1100ms tween, and is untouched by this swap.** `internal/gauge-reveal.ts:57-62` — `GAUGE_SPRING_FALLBACK = { kind: "spring", stiffness: 300, damping: 20, mass: 1 }`, consumed at `gauge.tsx:796,1088` as the second arg to `resolveEnterTransition`/`revealTiming`. This value is bklit's own `DEFAULT_NOTCH_ENTER_TRANSITION` (comment at gauge-reveal.ts:53-56) and has nothing to do with `REVEAL_DURATION_MS`/`REVEAL_EASE_CSS` — do not touch it as part of this package.
- **Terminal markers (line/area/composed's `ProjectionMarkerOverlay`) have their own 280ms default fade, not the 1100ms reveal.** `internal/terminal-marker.tsx:8-9,54-63` — `TERMINAL_MARKER_FADE_DURATION_MS = 280`, `TERMINAL_MARKER_FADE_EASING = "cubic-bezier(0.22,1,0.36,1)"`; `resolveTerminalTiming` only escalates to the shared `resolveEnterTransition`'s tween-resolution path (and thus indirectly to `TWEEN_FALLBACK`'s 1100ms as the ultimate default duration) when an explicit `enterTransition` prop of an incomplete tween shape is passed in. Untouched by this swap unless you find evidence a caller actually exercises that edge case at a default-props call site — verify before assuming it's live.
- `internal/candle-spring.ts` (candlestick) and `internal/sunburst-reveal.ts` (sunburst) — confirmed via direct grep to have **zero** references to `enter-transition`, `REVEAL_DURATION_MS`, or `REVEAL_EASE_CSS`. They are not in scope for this package at all; do not touch them.
