## The real risk: transition-timing desync. Answer this FIRST.

`go-to-plan.md:129` scopes this as *"opacity dims only; blur/scale stay custom."* That line
is correct but it has a cost it doesn't name. The dim is **one visual effect assembled from
several hand-tuned pieces** (`internal/hover-chrome.ts:35-41`):

| constant | value | note |
|---|---|---|
| `DIM_OPACITY` | `"0.3"` | chart-wide default |
| `DIM_TRANSITION` | `opacity 0.4s ease-in-out` | lines/areas |
| `BAR_DIM_TRANSITION` | `opacity 0.12s ease-in-out` | bars — **3.3× faster than lines** |
| `MARKER_DIM_OPACITY` | `"0.5"` | markers dim less far |
| `MARKER_DIM_BLUR_PX` | `2` | stays custom |
| `MARKER_DIM_TRANSITION` | `opacity 0.15s ease-in-out, filter 0.15s ease-in-out` | **co-transitions opacity AND filter in one declaration** |
| `MARKER_ACTIVE_SCALE` | `1.35` | stays custom |

The marker row is the problem. Opacity and blur are currently **inseparable** — one
transition string drives both, so they physically cannot drift apart. Move opacity to a
declarative native mechanism and blur stays imperative: now two timing sources, and they
*can* drift. Bars vs lines having different durations (0.12s vs 0.4s) also means a single
global native transition setting would be wrong for at least one of them.

**So your first task is a factual question, before any edit:**

> Is native `states` transition timing configurable **per mark**? If yes, how — a
> `transition`/`duration` field on the state entry, on the mark, on the spec, or only via
> CSS on the emitted element?

Answer it from the vendored source and its tests (`charts-core/src/`), not from assumption.
Then pick the outcome the evidence supports:

- **Timing configurable per-mark** → full swap. Reproduce 0.4s / 0.12s / 0.15s exactly.
- **Timing global-only or fixed** → **partial swap is the correct answer**: convert the
  marks whose timing the native mechanism can express (likely lines/areas/bars if a
  per-mark duration exists for them) and **leave markers imperative**, precisely because
  splitting their co-transitioned opacity+blur pair is a real regression risk for a
  cosmetic gain. Document the split and why.
- **No timing control at all, or `states` cannot express these values** → **documented
  non-viability is an acceptable, expected outcome.** Say so with the source evidence.
  P3.2 closed skipped-with-reason on exactly this basis and that was the right call. Do
  **not** force a cutover that changes dim timing to make the task look delivered.

A partial or negative result reported with evidence is worth more than a full swap that
silently retimes the dim.
