### 1. Grid guides are ALREADY native — only highlight rows remain

Verified directly against current source, `showcase/migrated/charts/internal/grid.ts:1-10` (header comment): *"TanStack's native `grid`/`ticks` axis-guide options render the ordinary grid lines (`.ts-chart__grid`); this module owns the config resolution... Highlight-row RENDERING is built by `internal/grid-highlight-mark.ts`."* This is not aspirational — it is current, wired behavior. `resolveGridGuide()` (`grid.ts:37-44`) output is consumed directly as native axis config at, e.g., `bar-chart.tsx:448,451-452` and `:622,625-626`:
```ts
x: { scale: xScaleFactory, grid: gridGuide.vertical, axis: { ticks: { count: gridGuide.columnTicks } } },
y: { ..., grid: gridGuide.horizontal, axis: { ticks: { count: gridGuide.ticks } } },
```
The same pattern repeats at `area-chart.tsx:549,707`, `line-chart.tsx:259,478`, `scatter-chart.tsx:528`, `candlestick-chart.tsx:515`, `composed-chart.tsx:974,993` — all six-plus cartesian charts already feed `resolveGridGuide()`'s `horizontal`/`vertical`/`ticks`/`columnTicks` straight into native `axis.grid`/`axis.ticks.count`. **The "ordinary grid lines" half of row 3 is done. Do not re-do it or claim it as new work.**

What genuinely remains: `internal/grid-highlight-mark.ts` (71 lines) — `gridHighlightRowMarks()` builds a **hand-written `createMark`** whose `render()` returns a manual `polyline` `SceneNode` per highlight row (lines 39-68), computing its own `path: M0,${row.y}L${innerWidth},${row.y}` string rather than using native `ruleY`. This is TanStack-native-shaped (it already goes through `createMark`/`ChartMark`/`SceneNode`) but is a custom mark, not the native `ruleY` rule primitive tanstack.md row 3 names. **This is the actual, narrower scope of this package's grid-guide half**: replace `gridHighlightRowMarks`'s hand-built polyline with native `ruleY`, preserving `resolveGridHighlightRows`'s value resolution (`grid.ts:56-69`, drops non-finite y per bklit's own guard) and the exact stroke/opacity/width/dasharray config resolution (`grid-highlight-mark.ts:31-34`, defaults: `var(--chart-foreground-muted)`, opacity 1, width 1, dasharray `"0"` i.e. solid).

The tick-count clamp (1–10) noted in tanstack.md's gap column stays app-side regardless — locate it (likely in the same chart files' tick-count resolution, not yet re-verified this round) and confirm it isn't dropped when highlight rows move to `ruleY`.

### 2. Funnel bands/lines — verify this is NOT viable before attempting it

`funnel-chart.tsx:1-30`'s own header comment (read in full) states funnel is a **deliberate plain-SVG fallback**, authorized by D30: *"docs/LOG.md D30 confirms FunnelChart is a GAP chart (TanStack has no funnel primitive)... Funnel's entire geometry is 100% pixel arithmetic with NO scale/domain anywhere... there is no cartesian/polar layout concept for `defineChart` to resolve at all... this file follows the D30-authorized escape clause... and ports bklit's own plain-SVG/div structure directly, same as ring.tsx/pie-chart.tsx/GaugeLinear."* Confirmed directly: funnel's grid bands (`<rect>` at `funnel-chart.tsx:721,723`) and grid lines (`<line>` at `:781,795`) are plain React-rendered SVG elements — **not TanStack marks at all**, because funnel is not wrapped in `<Chart>`/`defineChart` in the first place.

Native `bandX`/`bandY`+`ruleX`/`ruleY` marks require a cartesian host with a scale to resolve against. Funnel's own architecture doc-comment explicitly rules this out for the *whole component*, and doing it *only* for the grid bands/lines while leaving the rest of funnel plain-SVG would mean introducing a second, partial `<Chart>` host inside a component whose header comment argues at length against exactly that (a full re-quote: *"Wrapping a custom mark in `<Chart>` here would add an SVG layer, a scene-diff pass, and `data-ts-key` bookkeeping purely to re-derive numbers this component already computes directly from its own `ResizeObserver`, for zero behavioral benefit."*).

**This directly contradicts `research/phase-4/synthesis/tanstack.md` row 4's ★ (native-eligible) classification.** `research/phase-4/funnel.md`'s own per-chart inventory table marks funnel grid bands/lines "TS-NATIVE ... no" — i.e. CONTRADICTS-no, the opposite of tanstack.md's synthesized verdict. On direct verification, **`funnel.md`'s original verdict is correct and tanstack.md's synthesis is wrong for this one row** — the ★ upgrade appears not to have accounted for D30's explicit architectural ruling. **Do not attempt the funnel bands/lines native swap.** If your own investigation finds a way to do this that doesn't violate D30's ruling (e.g., a native primitive usable entirely outside a `<Chart>` host), report exactly what you found — but the default expectation for this package is that funnel is out of scope, and grid guides/highlight rows is the only real work here.
