# 04 — Metrics & Baselines

Status: **spec authored (Fable)** — implementation + baseline numbers to be filled by the bench-harness agent, reviewed by Fable.

## Goals (from PLAN.md)

Measure migration gains on three axes. Migrated components must be much closer to native TanStack Charts performance than to bklit-ui.

## Metrics

### M1 — Time to render (initial mount)

- **M1a mount-to-paint**: `performance.mark` immediately before React `root.render()` of the scenario → first paint after the chart's SVG is committed (double-`requestAnimationFrame` after mount effect). Excludes animation completion.
- **M1b settle time**: mount → chart visually settled (mount/reveal animations finished; detected via a scenario-exposed `window.__benchSettled` promise the component page resolves).
- **M1c scripting cost of mount**: total main-thread scripting time in the mount window (CDP `Performance.getMetrics` / trace slices).
- Data sizes: n = 100, 1 000, 10 000 points (per-chart-type appropriate shapes; fixed seeded generator).

### M2 — Runtime load (steady state)

- **M2a idle CPU**: main-thread task time during 5 s post-settle with no input. Catches always-running RAF loops / animation frameworks doing work at rest.
- **M2b heap**: `usedJSHeapSize` after settle + forced GC (Chromium `--js-flags=--expose-gc`).
- **M2c bundle cost**: min+gzip size of the scenario entry chunk attributable to the chart (Vite build, per-scenario entry).

### M3 — Onchange & interactivity

- **M3a data-update latency**: page exposes `window.__benchUpdate()` which swaps to a new seeded dataset (same n); measure update→paint over 30 updates, report median/p95.
- **M3b sustained update throughput**: drive updates every frame for 5 s (live-data scenario); report achieved FPS and dropped-frame %.
- **M3c hover cost**: Playwright dispatches a 60-step pointer sweep across the plot area (fixed coordinates, fixed cadence); measure per-pointermove main-thread time and frame times; report median frame time and worst frame. Tooltip must actually appear (asserted) so we measure the real path.
- **M3d brush/drag** (charts with brush): scripted drag across the track; frame-time distribution during drag.

## Harness design (deterministic, rerunnable)

- `bench/app/` — a Vite + React 19 app. One route per scenario: `/?impl=<bklit|tanstack|migrated>&chart=<name>&n=<points>&scenario=<mount|update|live|hover|brush>`. Each impl mounts the real component with identical seeded data (`bench/app/src/data.ts`, mulberry32 PRNG, fixed seed per chart+n).
- `bench/run.mjs` — Playwright (headed Chromium, fixed 1200×800 viewport, `--disable-frame-rate-limit` NOT used; we want real vsync) driving scenarios via CDP. Per scenario: 1 warmup run + 7 measured runs in fresh pages; report median (and p95 where relevant). Optional 4× CPU throttle flag for stability checks.
- Results written as JSON to `bench/results/<timestamp>/…` plus a `latest` symlink; `bench/report.mjs` renders the comparison table into `docs/BENCHMARKS.md`.
- Determinism rules: seeded data; fixed viewport & device-scale 1; animations run their natural course (M1b measures them); no network; each run in a fresh browser context; machine noise handled by medians across ≥7 runs.

### Baseline matrix (to be recorded)

For every chart in the migration checklist (research/01): `bklit` baseline and, where a native equivalent exists, `tanstack-native` baseline (plain TanStack chart, default styling — represents the performance ceiling). The `migrated` column is filled in during Phases 1–2 by rerunning the same scripts.

## Baseline results

Recorded 2026-07-30, Chromium 151.0.7922.34, macOS (Darwin 25.4.0), 1 warmup + 7 measured runs per combo, full tables in docs/BENCHMARKS.md (generated by `bench/report.mjs`; raw JSON in `bench/results/`). 24/24 pilot combos completed (line/area/bar/scatter × bklit/tanstack × n=100/1000/10000).

Headlines at n=1000 (median, bklit → tanstack-native):

| Chart | M1a mount→paint | M1b settle | M1c mount script | M2a idle script/5s |
|---|---|---|---|---|
| line | 66.3 → 27.9 ms (0.42×) | 1166 → 43 ms | 63.0 → 43.7 ms | 0.2 → 0.1 ms |
| area | 67.9 → 29.3 ms (0.43×) | 1162 → 42 ms | 62.4 → 47.3 ms | 0.2 → 0.0 ms |
| bar | 304.3 → 107.3 ms (0.35×) | 2466 → 178 ms | 1741 → 129 ms | 0.0 → 0.0 ms |
| scatter | 129.9 → 53.3 ms (0.41×) | 1291 → 85 ms | 579 → 64 ms | 0.0 → 0.0 ms |

Interpretation and caveats (Fable review):

- **M1b settle** difference is dominated by bklit's intentional 1100 ms reveal animation — it is a design feature, not pure overhead. The migrated components will keep the reveal (design parity), so their M1b will also be ~1100 ms+; the meaningful comparisons for migration gates are M1a, M1c, M2a, M3a, M3c, and M1b minus the animation duration.
- **bklit bar at n≥1000 is degenerate**: bar-slot width minus gap goes negative in a 1200 px viewport, producing hundreds of thousands of invalid-SVG console errors (negative `width`/`rx`) which themselves inflate M1c. Bar comparisons/gates use **n=100 only** until/unless a wider-viewport bar scenario is added; n≥1000 rows are kept in the tables for completeness but must not be used for gate math.
- **M3a (~32 ms) and M3c median (16.7 ms) floor at vsync** at small n for both impls — the update path is paint-bound at 1–2 frames of a 60 Hz display. Discriminating signals are M3a at large n and **M3c worst frame**.
- At **n=10000**, tanstack-native mounts slower than bklit for area (87.9 vs 70.4 ms M1a) and uses more heap (13.2 vs 5.4 MB), and its M3c worst frame spikes (≈1.3–1.4 s) — bklit's LTTB decimation (`decimate-time-series.ts`) caps rendered points while the naive tanstack scenario renders all 10 k. Migrated components should keep bklit's decimation layer in front of TanStack marks.
- **Tooltip detection flake**: one combo (bklit/line n=1000) recorded `tooltip: NO` in the matrix run; manual re-verification shows the tooltip appears reliably — the text-length heuristic raced the sweep cadence. Treat isolated `tooltip: NO` with manual re-check before failing a gate on it.
- M2c (bundle), M3b (live throughput), M3d (brush drag) remain stubbed in `bench/run.mjs` — to be implemented before Phase 2 charts need them (brush/live-line).
