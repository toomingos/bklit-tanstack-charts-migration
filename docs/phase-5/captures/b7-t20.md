## Why — three independent reasons, none of them pixel

1. **The WAAPI-retirement clause is unachievable.** `motion()`'s only group-level clip is
   `radialSweepClipPath(startAngle, sweep*progress, radius)` (`@tanstack/charts/dist/motion.js:995-1050`)
   — pie/arc only. The horizontal `inset(0 100% 0 0)` -> `inset(0 0 0 0)` wipe in `handleRender`
   has no native equivalent. Enter tracks are opacity fade / bar grow / path morph.
2. **`motion()` animates every data update.** `motion.js:612` derives `animate` from
   `motion2.resize || !resized` and never reads the definition's `animation` option
   (no `options.animation` / `resolveAnimation` reference exists in the module). Area-chart's
   documented policy is that new data paints immediately and only a y-domain change tweens.
3. **Nothing left to deliver (D400).** The spring half has zero in-scope call sites — all four
   spring tokens are consumed only by hover-chrome/tooltip modules, exempt under the acceptance
   clause's own residue rule. The tween half is a no-op: `REVEAL_DURATION_MS` = 1100 and
   `REVEAL_EASE_CSS` = `cubic-bezier(0.85,0,0.15,1)` already equal `motion.js`'s defaults exactly.

**Corrected from D388:** the renderer switch *does* exist and mounts cleanly —
`@tanstack/react-charts/dist/core.d.ts:1` exports `RendererChart` aliased `Chart`. It is
pixel-neutral. **T15 is therefore unblocked** and judged on its own merits.

## Root cause — found (D403)

Cross-correlating impl A against impl B over each diff's bounding box, at horizontal offsets
dx in [-3, 3], scoring mean absolute luma difference:

| chart | cell | diff px | bbox | best dx | SAD @ dx | SAD @ 0 |
|---|---|---|---|---|---|---|
| `line` | h50 | 518 | 138x37 | **+1** | **0.000** | 20.71 |
| `scatter` | h50 | 748 | 138x74 | **-1** | **0.018** | 13.42 |
| `composed` | h30 | 696 | 128x64 | **-1** | **0.001** | 17.99 |
| `area` | h50 | 537 | 474x41 | **-1** | **0.233** | 5.71 |

A residual of ~0 after a one-pixel shift means **identical content, offset by one pixel**. Confirmed
visually — both panels read `Fri, May 14 / seriesA 1,592.44` — and by edge detection: the panel's
left edge is at x=564 in A, x=563 in B. Scanline profiling shows the differing pixels are exactly
the two 11 px text rows plus the panel edge.

The **direction varies** (`line` +1, the rest -1), so this is not a systematic layout offset but a
**rounding race**: the panel's left edge rests near a half-pixel boundary and the two impls quantize
it differently on some runs. Each cell's non-zero mode is simply that panel's antialiased pixel
count (~500-750 px).

**Parity implication: these cells are measurement noise, not divergence.** A sub-pixel tooltip
placement difference of at most one device pixel is imperceptible and is not a design-parity
failure. This raises confidence in the migration — but the affected cells carry no information at
~500 px resolution, which is exactly why single-sample BASELINE comparison misled me.

## Standing rule from here

- A **hover-cell** reading is compared against the **mode distribution** in
  `qa/results/<chart>/*/report.json`, never against a single BASELINE sample. A change is
  attributed to an edit only when the value falls outside the cell's established mode set.
  **Re-running twice is explicitly insufficient.**
- **Settled cells remain the primary attribution signal** and are unaffected
  (`area` settled `3 x42/44`; `scatter` settled `4330/4329`).
- Claims of "bit-identical to BASELINE" made for *hover* cells in D394 / D396 / D398 are
  **over-stated** — consistent with no change, but not proof of it. The batch conclusions stand:
  they rest on source-level fidelity verification (byte-identical path templates, `displayName`

- **Root-causing the race is added to the 5.3.5 parked list (now 12 items) as its highest-value

# T15 — sunburst replay: NOT IMPLEMENTABLE (D404)

D388 re-sequenced T15 into B7 because all three of its mechanisms needed the renderer switch.
D401 removed that blocker, so T15 got a real audit. It fails on three independent grounds.

## 1. The radial sweep cannot express sunburst's choreography

Sunburst declares **one** mark — `radialArc<SunburstArcRow>(arcRows, { id: "sunburst-arcs", ... })`
(`sunburst-chart.tsx:616`) — and `polar.js` returns for it:

```js
nodes: [{ kind: "group", key: id, className: classes("ts-chart__arc", options.className),
          ariaHidden: true, children: nodes }]
```

a **single** `<g class="ts-chart__arc">` wrapping every row as sibling `area` nodes. So
`createArcTracks` (`motion.js:987-1005`) finds one group, derives one `{startAngle, sweep, radius}`
from `sceneArcGeometry` (which walks every child and accumulates the max sweep/radius across all
of them), and calls:

```js
timingFor({ phase: "enter", role, key: seriesKey, ..., datumIndex: 0, datumCount: 1, ... })
```

**`datumCount: 1` is decisive** — stagger keys off `datumIndex`/`datumCount`, so per-arc timing is
unavailable by construction. The whole sunburst gets one
`radialSweepClipPath(geometry.startAngle, geometry.sweep * progress, geometry.radius)` wedge on a
single progress curve.

What it would replace is per-arc:

| what | where | shape |
|---|---|---|
| keyframes | `internal/sunburst-reveal.ts:92-125` | 64 `d` samples sweeping **each arc's own** `a0 -> a0 + span*p`, radial extent held constant |
| stagger | `internal/sunburst-reveal.ts:45-73` | `delayMs = (ringIndex * 0.12 + index * 0.08) * scale * 1000`, bucketed by depth, ordered by clockwise fraction |
| driver | `sunburst-chart.tsx:741-746` | `liveEl.animate(keyframes, { duration: 1100, delay: delayMs, easing: "cubic-bezier(0.85,0,0.15,1)", fill: "backwards" })` per arc |

A single global wedge is a visibly different effect — a shape change, not a pixel-neutral swap —
at both mandated densities (n=27, n=33).

## 2. The D401 update-path problem bites harder here

```js
// motion.js:606-607
const resized = Boolean(previousScene &&
  (previousScene.width !== nextScene.width || previousScene.height !== nextScene.height));
// motion.js:612
const animate = !reduced && (initial ? ... : motion2.resize || !resized);
```

`resized` is true **only** on a width/height change, so any ordinary reconcile animates.
`arcRows` depends on `hoveredArc` (`sunburst-chart.tsx:607`), so the definition recomputes on
**every hover**. This is not hypothetical — the comment at `sunburst-chart.tsx:673-680` documents
exactly this as a fixed Wave-1 regression:

> Comparing a dataset stamp here fired on every hover and cleared `seen`, replaying the full
> 1100ms reveal on each pointer move.

`motion()` has no per-datum "already revealed" concept, so adopting it re-creates a regression this
project already measured and fixed.

## 3. No caller-facing replay hook exists

`RendererChart.d.ts:3-27` declares no `ref` and returns a plain `React.JSX.Element`;
`ChartRendererHost.update` (`dom-types.d.ts:213`) is unreachable from React. `motion.d.ts:7`
documents `initial: 'always'` as *"replay adopted server-rendered SVG"* — SSR hydration, not
on-demand replay. The only remaining lever is a `key` bump, which per `renderer.js:628` -> `:645`
destroys and remounts the entire surface — strictly more destructive than today's `playKey`,
additionally tearing down the `pointerleave` listener bound to the old `svg.ts-chart` node
(`sunburst-chart.tsx:811-824`, deps `[setHoveredArcIndex]`) and every in-flight WAAPI handle.

**Not a premise error.** D388 already noted T15's citations drift by one but name the right region.
This is the plan proposing a native mechanism the native renderer does not have.
